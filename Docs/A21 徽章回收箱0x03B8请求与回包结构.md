# A21 徽章回收箱 0x03B8 请求与回包结构

本文以 A21 `CmdPacketTypeA21.EMBLEM_COLLECT_ITEM`（枚举入口 `Network/Core/PacketTypesA21.cs` 第 2183 行，值 `0x03B8`）的**请求体**与**响应体**为主体，描述字段布局、客户端消费条件、当前服务端投影现状和未确认语义。包名与 opcode 一律以 `PacketTypesA21.cs` 为准，本文不另维护数字常量表。

所有客户端地址为**本机脱壳客户端的 IDA VA**。

## 1. 证据基线

- 客户端 dump：`/root/dfo_bin/S4A21脱壳+剥离TP/dnf.unpacked.crtfix.exe`（PE32，i386，`ImageBase = 0x400000`，无 ASLR）。该 dump 的**文件偏移 == RVA**，`IDA VA = RVA + 0x400000`。
- 与线上构建一致：`S4A21ClientPatch/GameGaurd/GameGaurd.cpp` 中 20 余处运行期静态补丁地址、`Extensions/GameNative/GameNative.cpp:26`（`kWindowFactoryAddress = 0x023BD910`）与该 dump 逐字节一致，可直接互证地址。
- 请求抓包：2026-10-10 实机 26 字节 body：

  ```text
  04 00 00 00 | 32 00 00 00 | 01 00 00 00 | 09 00 | 04 00 | 56 F0 28 00 | 09 00 | 8C DE F7 05
  ```

- 客户端文案真源：`dstr.dat` 资源 `FILE/102`（简体中文，运行时由 `[0x4E0EA1C] == 0` 选择）。解包与查询工具见 `dfo-ops/dnf-client-re/`。
- 客户端本地校验（使用窗口"使用"按钮时的前置检查）为 `VA 0x168D120`，其三条否决与本文第 3 节的 status 语义一一对应，见第 7 节。

证据等级：

1. **已确认消费**：读宽、顺序、目标由指令或稳定调用链证明。
2. **已确认作用**：后续代码证明 UI 刷新、弹窗或状态变更。
3. **待确认语义**：字段边界已知，但缺少实机或资源证据。

## 2. 请求体（客户端 → 服务端，26 字节）

### 2.1 唯一构造点

`VA 0x16F6130`，全客户端唯一的 `push 0x3b8` 发包点：

```asm
016F6141  mov  ebx, [ebp+8]        ; arg1 = 目标装备槽位
016F6150  mov  edi, [ebp+0xC]      ; arg2 = 箱子槽位
016F61EA  xor  ecx, ecx / xor eax, eax
016F61EE  mov  word ptr [ebp-0xC], cx    ; 缓冲 +0x14 = 0
016F61F5  mov  dword ptr [ebp-0x10], eax ; 缓冲 +0x10 = 0
016F61F8  mov  dword ptr [ebp-0xA], eax  ; 缓冲 +0x16 = 0
016F61FB  mov  word ptr [ebp-0x12], di   ; 缓冲 +0x0E = 箱子槽位
016F621C  mov  dword ptr [ebp-0x10], ecx ; 缓冲 +0x10 = 箱子模板 id
016F6227  mov  word ptr [ebp-0xC], bx    ; 缓冲 +0x14 = 目标装备槽位
016F6248  mov  dword ptr [ebp-0xA], ecx  ; 缓冲 +0x16 = 目标装备 uid
016F624D  push 0 / push 0x3b8 / call 0x274CA50 / call 0x274D1E0   ; BeginPacket
016F6263  lea  edx, [ebp-0x20]           ; 缓冲基址
016F6266  push 0x1a / push edx / call 0x274CED0                   ; Write(buf, 26)
016F6275  call 0x274E6D0                                          ; Send
```

缓冲基址是 `ebp-0x20`，函数对缓冲只写 `+0x0E .. +0x19` 共 12 字节。

### 2.2 字段表

| body 偏移 | 类型 | 字段 | 客户端是否写入 | 服务端可否使用 |
|---:|---|---|---|---|
| 0 … 13 | — | **无字段** | ❌ 从不写 | ❌ 栈残留，禁止依赖 |
| 14 | u16 | 箱子槽位（Main 列表） | ✅ | ✅ |
| 16 | u32 | 箱子模板 id | ✅ | ✅ |
| 20 | u16 | 目标物品槽位（Main 优先，其次 Equipment） | ✅ | ✅ |
| 22 | u32 | **目标物品模板 id（不是 uid）** | ✅ | ✅ |

⚠️ 命名纠正：`@22` 是**目标物品的模板 id**，不是实例 uid。`TryResolveEquipmentTarget`（`InventoryEquipmentMutationService.cs:1002`）的形参本名就是 `int itemTemplateId`，按「槽位 + 模板 id」在 Main、Equipment 中定位；handler 里的 `Request.TargetUid` 属命名错误，需一并改名。实测依据见第 2.4 节。

### 2.3 前 14 字节是栈残留（重要）

`0x16F6130` 是唯一构造者，它只显式初始化并填写第 2.2 节表中 `14/16/20/22` 四个字段，`+0x00..+0x0D` 既不初始化也不写值，直接由 `Write(buf, 26)` 原样发出。2026-10-10 抓包样例里那 14 字节恰好是 `4 / 0x32 / 1 / 9`，与真实值一致，属**巧合**（残留来源未定位），换一次调用路径就会不同（见第 2.4 节的实测）。

服务端解析 `Network/Handlers/InventoryHandler.EmblemCollect.cs` 的 `TryParseEmblemCollectBody` **只读 `14 / 16 / 20 / 22`**：`u16 箱子槽位`、`u32 箱子模板 id`、`u16 目标槽位`、`u32 目标物品模板 id`，另加 `箱/目标模板 id > 0`、槽位不超过 `short.MaxValue` 两个基本校验；**不读取也不校验前 14 字节**。

历史教训（同一文件曾按残留字节解析）：旧实现读 `u32@0 → boxSlot`、`u32@8 → count`、`u16@12 → targetSlot`，并要求它们与 `@14` / `@20` 相等，于是只要残留值与真实值不一致就整单被拒，表现为"玩家点了使用、箱子毫无反应"。该实现已废弃，回归用例见第 2.4 节与第 5 节。

## 3. 响应体（服务端 → 客户端）

### 3.1 客户端消费结构（已确认）

回包处理器 `VA 0x125A9F0`，注册点 `VA 0x125AF0C`：

```asm
0125AF0C  push ebx / push 0x125A9F0 / push 0x3b8 / call 0x1102C30
0125AF1C  mov  ecx, eax / call 0x1637660          ; 注册 (0x3B8 → 0x125A9F0)
```

处理器读取 **8 字节**参数（`call 0x27C5380`，`push 8`），首个 u32 为 **status**：

```asm
0125AA4A  call 0x27C5380          ; 取 8 字节
0125AA58  cmp  eax, 0             ; 首 u32 = status
0125AA5A  jne  0x125ABE0          ; status != 0 → 错误码分支
          … 成功路径：第 2 个 u32 作为"返还的徽章模板 id"，
             != -1 时构造道具对象并调用窗口方法 0x1259F90
0125ABE0  dec  eax / cmp eax, 4 / ja 0x125AC1C     ; status-1 > 4 → 静默返回
0125ABE6  jmp  dword ptr [eax*4 + 0x125AC38]       ; 5 项跳表
```

跳表 `0x125AC38` 与对应文案（文案取自 `dstr.dat` 资源 102）：

| status | 弹出文案 id | 文案 |
|---:|---|---|
| 0 | — | 成功分支（刷新窗口，不弹窗） |
| 1 / 3 / 5 | `0x11719` | 无法回收该装备的徽章 |
| 2 | `0x11718` | 装备上的徽章等级不同。 只适用于镶嵌了2个相同等级徽章的装备。 |
| 4 | `0x11716` | 只有镶嵌了2个徽章的装备(武器/防具/特殊装备)才能使用徽章回收箱。 |
| 其它 | — | 静默返回（读完 8 字节后什么都不做） |

弹窗链路与其它系统公告一致：

```asm
0125ABFD  push ebx / push 0x11719 / call 0x28C14C0    ; 按 id 取本地化文案
0125AC08  mov  ecx, [0x3A5C9B8]
0125AC11  push eax / push 0x209 / call 0x2304C70      ; 标题 id 0x209
```

即：**status 是客户端给玩家看的唯一反馈通道**；status 越界时玩家什么都不会看到。

### 3.2 服务端投影现状（已按本协议实现，2026-10-12）

`Network/Handlers/InventoryHandler.EmblemCollect.cs`：

| 场景 | 服务端 body | 客户端消费 |
|---|---|---|
| 成功 | `u32 status = 0` + `u32 返还的徽章模板 id`（8B，`BuildEmblemCollectAck`） | 走成功分支，用返还模板 id 刷新窗口 |
| 失败（解析失败或业务拒绝） | `u32 status` + `u32 0`（8B，`BuildEmblemCollectError`） | 按 status 弹第 3.1 节的对应文案 |

失败 status 默认 `1`（「无法回收该装备的徽章」）。服务端目前没有"必须 2 颗徽章""两颗等级相同"这两条规则，因此不会自然产生 `4` / `2` 两个码；为完成第 3.4 节的实机核对，另提供诊断开关 `DFO_EMBLEM_COLLECT_ERROR_STATUS=1..5` 强制失败回包的 status（默认未设置，验证完应保持未设置）。

历史实现（已废弃）：成功回 `01 | slot(i16) | uid(i32) | count(u8)`、失败回 2 字节 `{0x00, 0x04}`；两者客户端都读不懂（首 u32 越界 / 长度不足 8 字节），玩家因此既看不到成功反馈也看不到失败提示。当时"看起来正常"只是因为背包/装备刷新由服务端另外调用 `SendUpdateItemList` 单独发送，与回包内容无关。

### 3.3 实现要点

1. **成功**：`u32 status = 0` + `u32 返还的徽章模板 id`（客户端只读前 8 字节；如需附带槽位等，追加在其后，保持前 8 字节语义）。
2. **失败**：`u32 status = <码>` + `u32 0`。服务端的拒绝原因目前统一映射为 `1`；其余码留给规则扩展：

   | 服务端拒绝原因 | 映射 status | 玩家看到 |
   |---|---:|---|
   | 箱子模板/槽位不符、目标不是装备、装备被锁定、装备无徽章、背包已满（当前全部走这一档） | 1 | 无法回收该装备的徽章 |
   | 徽章数量不足（服务端若将来要求 2 颗才放行） | 4 | 只有镶嵌了2个徽章的装备…才能使用徽章回收箱。 |
   | 两颗徽章等级不同（服务端不判此条） | 2 | 装备上的徽章等级不同… |

3. **保留** `SendUpdateItemList` 的两次刷新，不要改成依赖客户端自刷新。
4. **响应体长度恒为 8 字节（成功失败都一样）**：客户端读取器是无边界校验的流式实现（游标 `[0x3BAAE38]`、剩余计数 `[0x3BAAE3C]`，读取函数 `VA 0x27C5380` 先 `memcpy` 再**无条件把游标前进 size**，之后才由 `VA 0x27C51D0` 检查剩余量并在负数时走缓冲重整路径），body 短于 8 字节会把命令体之外的字节读进来。

### 3.4 上线前必须做的实机确认（本文唯一的阻塞项）

第 3.1 节的结构来自客户端指令，但**"参数流游标在派发后正好停在我们 body 的第 0 字节"**这一点无法静态证明：设置游标的派发器在 VM 保护段内（引用 `[0x3BAAE38]` 的写点集中在 `.tp3` 段的 `0x4FD0114` 一片），本机无法把它读出来。第 3.2 节的回包已实现，但**客户端是否按 status 弹出文案尚未实机验证**，需要按下表确认（可用诊断开关 `DFO_EMBLEM_COLLECT_ERROR_STATUS` 逐码核对，无需改代码）：

| 步骤 | 服务端失败回包 body | 预期玩家看到 | 若未出现说明 |
|---|---|---|---|
| 1 | `04 00 00 00 00 00 00 00`（status=4） | 「只有镶嵌了2个徽章的装备(武器/防具/特殊装备)才能使用徽章回收箱。」 | 游标未对齐，或 status 不在第 0..3 字节 |
| 2 | `01 00 00 00 00 00 00 00`（status=1） | 「无法回收该装备的徽章」 | 同上 |
| 3 | `02 00 00 00 00 00 00 00`（status=2） | 「装备上的徽章等级不同。 只适用于镶嵌了2个相同等级徽章的装备。」 | 同上 |
| 4 | 成功回包 `00 00 00 00` + 返还徽章模板 id（小端 u32） | 面板刷新、无弹窗、不卡住 | 成功路径还读了别的字段 |

判据：**公告文案随 status 变化**即证明游标对齐且 status 语义正确（三种码对应三条不同文案，足以区分）；若三种码都没有任何反应，再试"body 前多带 1 个字节"的变体，说明派发器未消费掉某一层前缀。

### 3.5 实机状态（2026-10-12）

客户端已打补丁（第 2.4 节的三次请求即为补丁后实测）。已知事实与当前状态：

1. **客户端补丁生效**：客户端确实把 `0x03B8` 发出去了（打补丁前这些组合根本不会发包）——三条本地否决被跳过、`0x168D120` 返回成功、调用方走到发包点。
2. **服务端解析失败时玩家完全无感知**：三次请求都卡在旧的解析实现上，服务端回了 2 字节 `{0x00, 0x04}`，游戏内没有任何弹窗或提示 —— 这已经实测证明"短包 / 首 u32 越界 → 无反馈"。
3. **修复状态**：请求体解析已按第 2.3 节改好（只读 `14/16/20/22`），回包已按第 3.2 节实现（8 字节 status 协议），自测见第 5 节。剩下的待确认项只有第 3.4 节的"status 是否真的会显示成公告"。
4. 修复部署后，第 2.4 节的三帧预期结果为：第 1 帧（白金箱 + 单孔白金徽章 10095083/grade 4）成功、第 2 帧（华丽箱 `{2}` + 两颗灿烂 grade 3）业务层拒绝、第 3 帧（灿烂箱 `{3}` + 两颗灿烂）成功。

## 4. 服务端校验规则（决定回哪个 status）

入口 `Game/Inventory/Services/InventoryEquipmentMutationService.cs` 的 `TryCollectEquipmentEmblems`（第 245 行起），事务边界 `InventoryEquipmentAugmentationCommitService.TryCommitEmblemCollect`。

箱子允许的等级集合 = 箱子自身 `[action type]` 的参数（`TryResolveEmblemCollectorGrades`，第 1137 行）；徽章等级 = 该 stackable 的 `stackable.Grade`（`TryResolveEmblemGrade`，第 1161 行）。线上实测：

| 箱子 | 物品 id | 参数集合 |
|---|---:|---|
| 华丽的徽章回收箱 `stackable/emblem/chn_returnemblem.stk` | 2682963 | `[emblem collector] 2` |
| 灿烂的徽章回收箱 `stackable/emblem/chn_returnemblem1.stk` | 2682966 | `[emblem collector] 3` |
| 白金的徽章回收箱 `stackable/emblem/chn_returnemblem2_platinum.stk` | 2682964 | `[emblem collector] 4` |

判定矩阵：

| 箱子 | 装备上的徽章 | 结果 |
|---|---|---|
| 华丽 `{2}` | 2×华丽 (2,2) | 通过：返还 1 颗、销毁 1 颗、扣箱 1 |
| 华丽 `{2}` | 2×灿烂、或 1 华丽 + 1 灿烂 | 拒绝（存在等级不在集合内的徽章） |
| 灿烂 `{3}` | 2×灿烂 | 通过 |
| 灿烂 `{3}` | 2×华丽、或含白金徽章 | 拒绝 |
| 白金 `{4}` | 单孔 1×白金 | 通过：返还、不销毁 |
| 白金 `{4}` | 两孔 2×灿烂 | 拒绝 |
| 任意 | 装备无徽章 / 徽章槽为 0 / 目标非装备 / uid 不符 / 装备锁定 | 拒绝 |
| 任意 | 箱位放的不是这个箱子（模板不符或数量 0） | 拒绝 |
| 任意 | 返还时背包满 | 拒绝，且**零副作用**（不扣箱、不清槽） |

执行顺序：解析 → 校验 → `inventory.SetItem` 清空徽章槽并恢复占位 → 扣箱 → 组装结果；任一步失败都由事务回滚，不产生半成品。

注：服务端没有"两颗等级必须相同"这条规则，它是靠"参数集合通常单值"隐式满足的；若箱子参数写成多值（如官方孤儿文件里的 `4 5`），服务端会接受"两颗等级不同但都在集合内"的组合，此时比当年的客户端更宽松。

## 6. 仅作推测的语义

以下未取得实机或资源证据，不得写入业务代码、常量名或数据库字段：

- **8 字节参数的来源**：本文按"响应 body 起始即参数起始、无额外前缀"解释 `VA 0x27C5380` 的读取。读取器本身是**无长度校验的流式读取**（先 `memcpy`、再无条件前进游标、最后才检查剩余量），游标 `[0x3BAAE38]` 由 VM 保护段内的派发器设置，**本机无法静态证明派发后游标正好落在 body 第 0 字节**，也没有任何一次实机验证。这是本文最需要优先确认的一条，实验方法见第 3.4 节。
- **读取器的越界行为**：剩余量负数时进入缓冲重整路径（`VA 0x27C51D0`），是否因此吞掉后续命令字节未验证；由此得出第 3.3 节第 5 条"回包必须 ≥ 8 字节"的工程结论，但这只是规避而非已证明的机制。
- **status 1 / 3 / 5 的差异**：三条都映到同一文案 id，客户端如何区分（或是否有区分）未知；建议服务端只使用 1、2、4。
- **status 越界时的静默行为**：现有服务端回包正落入该档（首 u32 既非 0 也非 1..5），因此"没有反馈"是可解释的，但没有实机录像逐帧确认。
- **请求体前 14 字节残留的来源**：未定位；`0x32`（=50）与构造函数的常量巧合，不足以证明来源。
- **"徽章等级"口径**：服务端用 `stackable.Grade`，客户端按 `ItemTable(徽章id)[+8]` 取等级。两者是否同一字段未对照；打客户端补丁后判定权在服务端，该口径差异不再影响能否回收，但会影响"两侧拒绝文案是否一致"。
- **客户端本地校验的三条否决**（`VA 0x168D120`）为：① 每个徽章孔都必须有徽章（文案 `0x11716`）；② 第 1 颗徽章等级必须属于箱子参数集合（`0x11719`）；③ 两颗徽章等级必须相等（`0x11718`）。三条与第 3.1 节的 status 文案同源，但**服务端不复现第 ③ 条**。
